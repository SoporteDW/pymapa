Seguimos con DT-02 · Gestionar datos con calidad y disponibilidad. Esta capacidad merece especial cuidado porque “tener datos” no equivale a poder utilizarlos, y porque sería muy fácil absorber aquí integración, analítica, seguridad o gobierno de datos completo.
# DT-02 · Gestionar datos con calidad y disponibilidad
## Dimensionamiento orgánico
La pregunta irreducible será:
¿Dispone la organización de los datos materialmente necesarios, con calidad, significado, oportunidad y disponibilidad suficientes para los usos que deben soportar?
La familia ISO 8000 proporciona una base particularmente apropiada: ISO 8000-1:2022 establece principios de calidad de información y datos y continúa vigente tras su confirmación en 2024; ISO 8000-8 aborda conceptos y medición de calidad, e ISO/TS 8000-82:2022 trata la formulación de reglas de datos para preservar su integridad y confiabilidad. ISO
DAMA aporta una segunda referencia relevante porque distingue explícitamente calidad, integración/interoperabilidad, seguridad, metadata y governance como áreas relacionadas pero diferentes. Esa separación es muy útil para mantener limpias las fronteras DT-02/03/05. Además, su revisión reciente incorporó currency como dimensión reconocida de calidad y explicitó los Critical Data Elements. DAMA International®

# 2. Identidad
## Definición V1
DT-02 evalúa la capacidad de la organización para identificar los datos materialmente necesarios y mantenerlos con calidad, significado, disponibilidad y oportunidad suficientes para los usos de negocio, operación, control o decisión a los que deben servir.
## Unidad de análisis
No será:
“la base de datos”.
Tampoco:
“el sistema donde están los datos”.
Será:
la correspondencia entre una necesidad material de datos, el conjunto de datos que pretende satisfacerla y su aptitud efectiva para el uso requerido.
Cadena:
Uso material → necesidad de datos → dato requerido → significado → captura/origen → calidad → disponibilidad → oportunidad → uso posible.

# 3. El objeto no es DATA en abstracto
Introducimos:
### DATA NEED
Dato requerido para satisfacer un uso material determinado.
### DATA ELEMENT
Unidad de información suficientemente distinguible para evaluar su condición.
Puede ser:
- cliente;
- producto;
- precio;
- inventario;
- pedido;
- fecha;
- vendedor;
- costo;
- pago;
- dirección;
- estado;
- cantidad;
- evento;
- indicador base.
No significa que Pymapa deba construir un catálogo empresarial completo.

# Critical Data Element
Adoptamos conceptualmente:
### CDE-PYM
Elemento de dato cuya ausencia, error, ambigüedad, desactualización o indisponibilidad puede producir una consecuencia material en un uso aplicable.
Esto permite aplicar el principio:
gestionar con mayor profundidad los datos que más importan.
No todos los campos de una pyme necesitan el mismo gobierno.

# 4. Modelo de estado del dato
Necesitamos distinguir:
EXISTS ≠ CAPTURED ≠ DEFINED ≠ VALID ≠ CURRENT ≠ AVAILABLE ≠ FIT-FOR-USE
Ejemplo:
La empresa tiene la dirección del cliente.
EXISTS: sí.
Pero:
corresponde a una dirección antigua.
Entonces puede ser:
CAPTURED = YES
AVAILABLE = YES
CURRENT = NO
FIT-FOR-USE = NO
Otro ejemplo:
El dato existe correctamente en el ERP, pero quien prepara una entrega no puede obtenerlo a tiempo.
Entonces:
QUALITY = SUFFICIENT
AVAILABILITY FOR USE = INSUFFICIENT

# 5. Quality ≠ perfection
Éste será uno de los principios centrales.
Un dato no necesita ser:
absolutamente perfecto
para ser útil.
Necesita ser:
suficientemente bueno para el uso material correspondiente.
### P-DT02-CORE-01
La calidad de un dato debe evaluarse respecto de los requisitos del uso al que sirve, no mediante una expectativa universal de perfección.

# Ejemplo
Edad del cliente:
“entre 35 y 44 años”
puede ser suficiente para:
segmentación de marketing.
Pero insuficiente para:
verificar un requisito legal basado en fecha exacta de nacimiento.
Mismo dato conceptual.
Distinto uso.
Distinta suficiencia.

# 6. Aplicabilidad y materialidad
DT-02 no exige evaluar todos los datos.
### APP-DT02-01
La profundidad de evaluación debe seguir la materialidad del uso y de las consecuencias asociadas a una condición insuficiente del dato.
Factores de materialidad:
- criticidad del proceso;
- relevancia para decisiones;
- impacto financiero;
- impacto sobre cliente;
- frecuencia;
- volumen;
- dependencia aguas abajo;
- riesgo;
- dificultad de corrección;
- uso regulatorio cuando aplique.
No forman todavía un score universal.

# 7. Fronteras
## DT-02 vs DT-03
Supongamos:
nombre del cliente correcto en CRM, pero distinto en facturación.
DT-02 puede detectar:
inconsistencia del dato.
DT-03 puede encontrar:
falla de integración/sincronización entre aplicaciones.
La observación puede reutilizarse.
La conclusión causal no.

## DT-02 vs DT-04
DT-02:
¿los datos necesarios son suficientemente utilizables?
DT-04:
¿se convierten en información que permite tomar una decisión?
Datos excelentes no garantizan:
buena información o buena decisión.
Y una decisión puede en ocasiones funcionar con datos imperfectos pero suficientes.

## DT-02 vs DT-05
DT-02 pregunta:
¿el dato está disponible para quien legítimamente necesita utilizarlo?
DT-05 preguntará:
¿está adecuadamente protegido y puede preservarse/recuperarse frente a amenazas o interrupciones?
Por tanto:
AVAILABILITY-FOR-USE ≠ SECURITY ≠ RESILIENCE.

## DT-02 vs DT-01
Un sistema puede funcionar perfectamente:
DT-01 positivo,
mientras contiene datos deficientes:
DT-02 negativo.

## DT-02 vs OP
Una persona introduce repetidamente un código equivocado.
Antes de concluir:
“problema de calidad de datos” como causa raíz,
debemos poder distinguir:
- diseño del formulario;
- proceso;
- definición ambigua;
- falta de validación;
- competencia;
- integración;
- dato fuente.
DT-02 identifica la condición del dato.
La causalidad puede cruzar capacidades.

# 8. Modelo de calidad Pymapa
No necesitamos imponer una lista universal de dimensiones sobre cada dato.
Proponemos 7 características potenciales.
### DQ-01 · Completeness
¿Está presente lo necesario?
### DQ-02 · Accuracy
¿Representa suficientemente la realidad/referencia que pretende representar?
### DQ-03 · Consistency
¿Mantiene compatibilidad suficiente entre representaciones relevantes?
### DQ-04 · Validity
¿Cumple las reglas/formato/dominio aplicables?
### DQ-05 · Currency
¿Está suficientemente actualizado para el uso?
### DQ-06 · Uniqueness/Identity
¿Podemos distinguir suficientemente entidades/registros cuando el uso lo requiere?
### DQ-07 · Meaning/Interpretability
¿Se entiende suficientemente qué representa el dato y cómo debe interpretarse?
Pero:
no todo CDE necesita ser evaluado contra las siete características.
El uso determina cuáles son materiales.

# Availability
La disponibilidad necesita su propia descomposición:
### DA-01 · LOCATABLE
Sabemos dónde está.
### DA-02 · ACCESSIBLE
El usuario/caso legítimo puede obtenerlo.
### DA-03 · TIMELY
Puede obtenerlo dentro del horizonte requerido.
### DA-04 · USABLE
Se presenta en una forma suficientemente utilizable.
Esto genera otra separación:
LOCATABLE ≠ ACCESSIBLE ≠ TIMELY ≠ USABLE.

# Provenance
La procedencia puede importar cuando es necesaria para establecer:
- confiabilidad;
- significado;
- actualidad;
- autoridad;
- transformación;
- trazabilidad.
Pero no exigiremos lineage enterprise para todos los datos.
### P-DT02-01
La profundidad de provenance requerida debe ser proporcional a la materialidad del dato y a cuánto depende de ella la confianza en su uso.
ISO 8000-110, por ejemplo, señala que aspectos como exactitud y provenance deben tratarse como parte de una estrategia global de calidad de datos, aunque esa norma específica se centre en intercambio de master data. ISO

# 10. Information Needs
Resultan 17 NI correspondientes a las VA.
No obstante, una NI merece explicitación especial:
### NI-DT02-USE
Antes de preguntar:
“¿qué tan buena es la calidad de sus datos?”
debemos saber:
¿para qué dato y para qué uso?
Sin esa información, Pymapa no debe emitir un diagnóstico fuerte de calidad.

# 11. Grounding
La arquitectura externa queda especialmente sólida.
### ISO 8000
ISO 8000-1:2022 proporciona los principios generales y la ruta hacia calidad de datos; fue confirmada en 2024. ISO 8000-8:2015 cubre conceptos fundamentales y prerrequisitos de medición, mientras ISO/TS 8000-82:2022 aborda reglas de datos y profiling. ISO
La familia continúa evolucionando: ISO tiene actualmente en desarrollo ISO/AWI 8000-3, concebida para cubrir procesos que generan, obtienen, validan, transforman, conservan, recuperan, distribuyen y eliminan datos, además de planificación, control, aseguramiento y mejora de calidad. Esto justifica crear un trigger de revisión, no anticipar su contenido como norma vigente. ISO
### DAMA
DAMA distingue Data Quality de Data Integration & Interoperability, Data Security, Metadata y Data Governance. Su revisión también incorpora explícitamente currency y Critical Data Elements. DAMA International®
No convertiremos DAMA-DMBOK en requisito para la pyme.
Lo utilizamos como:
fuente profesional de contraste conceptual.

# 13. Captura progresiva
## P1 · Núcleo
No preguntaremos:
“¿cuál es su nivel de data governance?”
Preguntaremos:
“¿Qué información necesita para operar o decidir y suele faltar?”
“¿Qué datos generan errores o retrabajo?”
“¿Hay datos que distintas personas interpretan de manera diferente?”
“¿Qué información suele llegar demasiado tarde?”
“¿Qué dato equivocado tendría consecuencias importantes?”
Estas preguntas permiten descubrir CDE candidatos.

# P2 · Condicional
Se activa ante:
- retrabajo;
- correcciones frecuentes;
- datos faltantes;
- duplicados;
- diferencias entre reportes;
- información desactualizada;
- búsqueda manual recurrente;
- múltiples archivos;
- definiciones distintas;
- decisiones retrasadas;
- errores de cliente/producto/inventario;
- conciliaciones frecuentes;
- dependencia de una persona para interpretar datos.

# P3 · Discriminación
Ante:
“los datos no cuadran”
debemos distinguir:
CAPTURE QUALITY
DEFINITION/SEMANTIC GAP
DATA QUALITY
INTEGRATION/SYNCHRONIZATION → DT-03
TRANSFORMATION/ANALYTICS → DT-04
PROCESS EXECUTION → OP
COMPETENCE → PC-02
TECHNOLOGY → DT-01

# P4 · Contradicciones
### CONTR-DT02-01
DECLARED_DATA_QUALITY_vs_RECURRING_CORRECTIONS
“Nuestros datos están bien”
pero existe corrección manual recurrente material.
### CONTR-DT02-02
SINGLE_SOURCE_vs_MULTIPLE_MEANINGS
Existe “fuente única”, pero distintos usuarios interpretan el campo de manera diferente.
### CONTR-DT02-03
AVAILABLE_DATA_vs_LATE_FOR_USE
El dato existe, pero llega después de la decisión.

# P5 · Validación
En lugar de:
“¿sus datos son confiables?”
podemos validar:
“Para confirmar inventario antes de vender, ¿este dato refleja suficientemente la disponibilidad real en el momento en que el vendedor toma la decisión?”
Ahora tenemos:
DATA + USE + TIME + SUFFICIENCY.

declaración consistente.
### EVID-DT02-01
La exigencia de evidencia aumenta con la consecuencia material de utilizar un dato insuficiente.

# 15. Suficiencia
### SUFF-DT02-01
La capacidad alcanza suficiencia cuando los datos materialmente necesarios para los usos aplicables satisfacen sus requisitos críticos de calidad y disponibilidad, sin incertidumbres pendientes capaces de cambiar materialmente la conclusión.
No significa:
todos los datos perfectos.

# Coverage
La cobertura debe seguir:
material uses → critical data → applicable quality requirements.
No:
todos los campos → todas las dimensiones.
Este cambio reduce muchísimo la carga diagnóstica.

# 16. Confianza
Para un dato crítico, la confianza puede progresar:
C0 · desconocido
C1 · declarado
C2 · evidencia/muestra consistente
C3 · condición observada/repetida suficientemente
No creamos una escala nueva: reutilizamos el servicio genérico C0–C3 del Motor.

# Guardrails
- No evaluar calidad sin conocer el uso.
- No exigir perfección.
- No evaluar todos los datos con todas las dimensiones.
- No asumir que duplicado = error.
- No asumir que dato faltante = brecha material.
- No confundir consistencia con exactitud.
- No confundir formato válido con dato correcto.
- No confundir existencia con disponibilidad.
- No confundir disponibilidad con oportunidad.
- No confundir calidad con integración.
- No confundir calidad con analítica.
- No confundir acceso legítimo con seguridad.
- No exigir catálogo de datos enterprise.
- No exigir data steward formal por defecto.
- No exigir herramienta de Data Quality.
- No penalizar controles manuales cuando son suficientes.
- No premiar automatización por sí misma.
- No exigir lineage completo cuando provenance mínima es suficiente.
- No utilizar volumen de datos como proxy de madurez.
- No declarar “dato confiable” únicamente porque proviene del sistema oficial.

# Candidatos para el Motor
### CAND-MOTOR-DT02-01
La calidad del dato debe evaluarse respecto de un uso material y sus requisitos, no en abstracto.
### CAND-MOTOR-DT02-02
Existencia, captura, definición, validez, actualidad, disponibilidad y fitness-for-use deben mantenerse como estados diferentes.
### CAND-MOTOR-DT02-03
Las dimensiones de calidad aplicables deben activarse condicionalmente por Data Need/CDE y uso.
### CAND-MOTOR-DT02-04
Un mismo dato puede ser suficientemente bueno para un uso e insuficiente para otro.
### CAND-MOTOR-DT02-05

### CAND-MOTOR-DT02-06
La profundidad de provenance y trazabilidad requerida debe aumentar con materialidad y dependencia de esas propiedades para establecer confianza.

## El finding debe conservar el uso
No deberíamos generar:
“El dato de inventario tiene baja calidad.”
Mejor:
“La disponibilidad de inventario utilizada para confirmar pedidos presenta diferencias suficientemente frecuentes/materiales respecto de existencias reales para comprometer la confirmación comercial.”
La segunda formulación contiene:
DATA + USE + CONDITION + CONSEQUENCE
y permite intervenir mejor.
### FIND-DT02-01
Un finding de calidad de datos debe preservar la relación con el uso material que justificó su evaluación.

# Calidad observada ≠ causa
Supongamos:
18 % de las direcciones de entrega contienen errores.
Esto es una observación.
Las causas posibles incluyen:
- captura manual;
- definición;
- formulario;
- validación;
- dato fuente;
- integración;
- actualización;
- proceso;
- usuario;
- transformación.
Pymapa no debe saltar directamente a:
“capacitar a quien captura”.
### CAUS-DT02-01
La condición insuficiente del dato y la causa que la produce deben permanecer como objetos distintos hasta existir evidencia causal suficiente.

# Vocabulario de decisión
DT-02 necesita 12 direcciones posibles.
### DEFINE
Definir dato/significado/requisito.
### CAPTURE
Comenzar a obtener un dato material faltante.
### VALIDATE
Introducir una validación proporcional.
### CORRECT
Corregir datos existentes cuando sea necesario.
### PREVENT
Modificar el mecanismo que genera errores.
### STANDARDIZE
Resolver diferencias materiales de definición/formato/dominio.
### RECONCILE
Resolver discrepancias entre representaciones cuando corresponda.
### ENABLE_ACCESS
Habilitar localización/acceso oportuno.
### REFRESH
Actualizar datos cuya vigencia sea insuficiente.
### TRACE
Fortalecer provenance/trazabilidad cuando material.
### MONITOR
Detectar deterioro material.
### NO_ACTION
Aceptar la condición cuando sigue siendo suficientemente apta para el uso.

# Corrección vs prevención
Ésta debe ser una distinción explícita.
CORRECTIVE DATA ACTION ≠ PREVENTIVE DATA ACTION
Ejemplo:
CORRECTIVE
limpiar 500 registros de clientes.
PREVENTIVE
modificar el mecanismo que genera duplicados.
Una intervención puede necesitar ambas.
Pero si hacemos solo la primera:
el problema puede reaparecer.

# Principio Source-First
Introducimos:
### INT-DT02-01 · SOURCE-FIRST CORRECTION
Cuando sea razonable y causalmente sustentado, debe preferirse corregir el mecanismo que genera o deteriora un dato material antes que depender indefinidamente de correcciones posteriores.
Pero tampoco será dogma.
Si el problema ocurre:
tres veces al año
y corregir manualmente cuesta:
dos minutos,
una corrección manual puede ser perfectamente suficiente.

# Minimum Sufficient Data Control
Segundo principio:
### INT-DT02-02
La intervención debe utilizar el mecanismo de control menos complejo que mantenga el dato suficientemente apto para su uso material.
Puede ser:
- regla verbal clara;
- campo obligatorio;
- lista desplegable;
- validación;
- revisión humana;
- conciliación;
- automatización;
- master data;
- control técnico.
La solución depende de:
materialidad + frecuencia + volumen + consecuencia + costo de control.

# Tolerancia
Aquí aparece un objeto importante:
### DATA QUALITY TOLERANCE
No siempre queremos:
error = 0.
Podemos necesitar:
error ≤ nivel que no compromete materialmente el uso.
Ejemplo sencillo:
Para marketing exploratorio puede tolerarse cierto porcentaje de datos incompletos.
Para:
número de cuenta utilizado para realizar pagos,
la tolerancia puede ser muchísimo menor.
### CAND-MOTOR-DT02-08
Las reglas de calidad deben poder incorporar tolerancias dependientes del uso y materialidad, en lugar de asumir perfección binaria.

# KPI
Podrían utilizarse:
- % completitud;
- tasa de error;
- duplicados;
- edad del dato;
- discrepancias;
- tiempo de actualización;
- tiempo de disponibilidad;
- correcciones;
- recurrencia de issues;
- costo de retrabajo.
Pero ningún KPI es universal.
Incluso:
98 % de accuracy
no tiene significado suficiente sin saber:
cuál 2 % está equivocado y para qué se usa.

# Validación
DT-02 necesita cinco estados.
### V0 · UNKNOWN
Condición desconocida.
### V1 · DEFINED
Dato, uso y requisitos suficientemente definidos.
### V2 · QUALITY-EVIDENCED
Muestra/evidencia demuestra calidad suficiente.
### V3 · FIT-FOR-USE
El dato funciona suficientemente dentro del uso real.
### V4 · SUSTAINED
La suficiencia se mantiene mediante controles proporcionales durante el horizonte relevante.

# Validación por uso
Igual que DT-01, no validamos simplemente:

Customer Email → campañas → V3

Customer Address → entregas → V1.

El estado de validación debe asociarse a DATA ELEMENT + USE, no únicamente al dato en abstracto.
Esto tiene consecuencias importantes para el futuro modelo de conocimiento.

# 12. Contextualización, Knowledge Governance y cierre
## Contextualización
DT-02 debe escalar con:
data materiality × operational complexity
y no simplemente con número de empleados.
Una empresa de ocho personas que opere una plataforma digital puede necesitar controles de datos sofisticados.
Una empresa de ochenta personas con procesos simples puede requerir menos.

# Gobierno de datos proporcional
Pymapa no exigirá automáticamente:
- Chief Data Officer;
- Data Governance Council;
- Data Steward formal;
- catálogo corporativo;
- MDM;
- Data Lake;
- data mesh;
- observability platform.
Pero sí debe poder establecer:
quién puede resolver una condición material del dato.
Podemos representar esto simplemente como:
### DATA ACCOUNTABILITY
persona/rol con capacidad suficiente para decidir o coordinar tratamiento del dato aplicable.
La formalidad depende del contexto.

# Ownership: precaución semántica
“Data owner” puede significar cosas distintas entre organizaciones.
Por eso Pymapa debe preguntar funcionalmente:
“¿Quién puede decidir qué significa este dato o cómo debe corregirse?”
antes de preguntar:
“¿Quién es el Data Owner?”
### P-DT02-18
La existencia de accountability funcional importa más que la existencia del título formal de Data Owner.

# AI y datos
La relación con IA merece un control explícito.
Un dataset puede ser:
suficientemente bueno para reporting
pero:
insuficiente para entrenar, evaluar o alimentar un sistema de IA.
Esto sigue nuestra regla:
fitness depends on use.
Por tanto, en DT-06/Fase 3 podremos reutilizar:
DATA + USE + QUALITY EVIDENCE
pero no heredar automáticamente:
“datos aptos”.
