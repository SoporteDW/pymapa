Seguimos con DT-03 · Integrar datos, aplicaciones y flujos de información. Esta capacidad tiene una trampa conceptual importante: si medimos integración por número de APIs, automatizaciones o sistemas conectados, premiaríamos complejidad tecnológica en lugar de capacidad empresarial.
# DT-03 · Integrar datos, aplicaciones y flujos de información
## Dimensionamiento orgánico
La pregunta irreducible será:
¿La información material puede atravesar suficientemente las fronteras entre personas, procesos, datos y aplicaciones que necesita cruzar para que el trabajo funcione de extremo a extremo?
Por tanto:
DT-03 no mide conectividad tecnológica. Mide continuidad suficiente de información a través de fronteras relevantes.
Una integración manual puede ser suficiente. Una API puede ser insuficiente.

Avanzamos ahora con SET A completo.

# 2. Identidad
## Definición V1
DT-03 evalúa la capacidad de la organización para lograr que datos e información materialmente necesarios circulen entre aplicaciones, procesos, personas o actores relevantes con suficiente integridad, oportunidad, correspondencia y control para sostener el flujo de trabajo requerido.
## Unidad de análisis
No será:
la integración entre dos sistemas.
Será:
el cruce material de información a través de una frontera necesaria para un flujo de trabajo o uso determinado.
Lo denominamos:
### INFORMATION HANDOFF
Transferencia material de información desde un origen hacia un destino que necesita recibirla o utilizarla para continuar correctamente un flujo aplicable.
Cadena:
Flow Need → Source → Information → Boundary → Transfer → Transformation → Destination → Use → Confirmation/Exception.

# 3. Integración ≠ API
Éste será el principio central.
Un Information Handoff puede producirse mediante:
### IH-MANUAL
Una persona transfiere información.
### IH-FILE
Archivo, exportación/importación.
### IH-SHARED
Fuente compartida.
### IH-AUTOMATED
Automatización entre herramientas.
### IH-API
Interfaz entre aplicaciones.
### IH-EVENT
Evento/mensaje.
### IH-HYBRID
Combinación.
Ninguno es intrínsecamente superior.
### P-DT03-CORE-01
El mecanismo de integración debe evaluarse por su suficiencia para el flujo material, no por su sofisticación técnica.

# Ejemplo
Una empresa procesa:
cuatro órdenes especiales al mes.
Una persona exporta un archivo, lo revisa y lo carga al sistema del proveedor.
Si funciona:
- oportunamente;
- sin errores materiales;
- con esfuerzo proporcional;
puede ser completamente suficiente.
Automatizarlo puede destruir valor.
Pero si existen:
4.000 órdenes diarias,
el mismo mecanismo puede ser claramente insuficiente.

# 4. Integración como continuidad de información
Necesitamos separar:
CONNECTED ≠ TRANSFERRED ≠ MAPPED ≠ SYNCHRONIZED ≠ RECEIVED ≠ USABLE ≠ CONFIRMED
Dos sistemas pueden estar técnicamente conectados pero:
enviar campos equivocados.
O:
transferir correctamente una vez al día cuando el proceso necesita tiempo real.
O:
transferir información sin saber qué hacer cuando falla.
Por tanto:
### INTEGRATION FIT
grado en que un Information Handoff satisface suficientemente los requisitos del flujo al que sirve.

# 5. Aplicabilidad
No toda frontera necesita integración.
### APP-DT03-01
DT-03 se activa cuando un uso o flujo material depende de que información atraviese una frontera entre fuentes, aplicaciones, procesos, personas o actores.
Si la información:
nace y se utiliza suficientemente dentro del mismo contexto,
puede no existir necesidad material de integración.

# Materialidad
Aumenta con:
- volumen;
- frecuencia;
- criticidad;
- sensibilidad temporal;
- retrabajo;
- consecuencia del error;
- número de destinos;
- dependencia aguas abajo;
- complejidad de transformación;
- necesidad de consistencia;
- dificultad de recuperación;
- crecimiento previsto.
Otra vez:
no forman un score universal.

# 6. Fronteras
## DT-03 vs DT-02
DT-02:
¿el dato es suficientemente apto?
DT-03:
¿puede atravesar correctamente las fronteras necesarias?
Ejemplo:
CRM tiene dirección correcta.
ERP tiene dirección antigua.
Puede existir:
DT-02 inconsistency.
Pero la causa puede ser:
DT-03 synchronization failure.

# DT-03 vs OP-03
Esta frontera es especialmente importante.
OP-03:
¿el proceso funciona integrado de extremo a extremo?
DT-03:
¿la información cruza suficientemente las fronteras que ese proceso requiere?
Un proceso puede estar mal diseñado aunque los sistemas intercambien datos perfectamente.
Y un proceso bien diseñado puede fallar porque:
la información no llega.
### P-DT03-01
Integración de información habilita integración de procesos, pero no la sustituye.

# DT-03 vs OP-04
OP-04:
¿conviene simplificar/automatizar?
DT-03:
¿el handoff actual es suficiente?
Si no lo es, la intervención podría ser:
mejorar el handoff manual,
no necesariamente automatizarlo.

# DT-03 vs DT-01
DT-01:
aplicaciones adecuadas individualmente.
DT-03:
funcionamiento suficiente entre ellas.
Podemos tener:
DT01 = positive
DT03 = negative.

# DT-03 vs DT-04
Un pipeline puede transportar correctamente información.
Eso no demuestra que:
la organización la convierta en información útil para decidir.

# DT-03 vs DT-05
DT-03 puede evaluar:
que la transferencia ocurra.
DT-05 evaluará:
protección, riesgo y continuidad.
Un intercambio técnicamente efectivo puede ser:
inseguro.

# 7. Tipología de fronteras
Introducimos 6 tipos funcionales, no tecnológicos.
### BND-01 · APPLICATION
Aplicación ↔ aplicación.
### BND-02 · DATA
Fuente/conjunto ↔ otro contexto de datos.
### BND-03 · PROCESS
Etapa ↔ etapa.
### BND-04 · HUMAN-SYSTEM
Persona ↔ sistema.
### BND-05 · HUMAN-HUMAN
Persona/rol ↔ persona/rol cuando el handoff informacional es material.
### BND-06 · EXTERNAL
Organización ↔ cliente/proveedor/plataforma/tercero.
Esto es importante porque una pyme puede tener una brecha de integración aunque:
solo utilice una aplicación.
Por ejemplo:
ventas anota una instrucción en comentarios y operaciones nunca la ve.
Es una falla material del flujo de información.

# 8. Requisitos del handoff
Un Information Handoff puede necesitar:
### HR-01 · CONTENT
Transferir lo necesario.
### HR-02 · MAPPING
Mantener correspondencia semántica suficiente.
### HR-03 · TIMING
Llegar dentro del horizonte requerido.
### HR-04 · FREQUENCY
Actualizar con frecuencia suficiente.
### HR-05 · SEQUENCE
Ocurrir en el punto correcto del flujo.
### HR-06 · INTEGRITY
No perder/alterar materialmente información.
### HR-07 · CONFIRMATION
Permitir conocer suficientemente si ocurrió cuando esto es material.
### HR-08 · EXCEPTION
Tratar fallos/excepciones proporcionalmente.
No todos aplican a todos los handoffs.

# 9. Transformación
Transferencia no siempre significa:
copiar exactamente.
Puede requerir:
- convertir formato;
- agregar;
- separar;
- mapear código;
- transformar unidad;
- enriquecer;
- resumir;
- filtrar.
Por tanto:
TRANSFORMATION ≠ CORRUPTION.
Una transformación es correcta cuando preserva:
el significado requerido por el uso destino.
### P-DT03-02
La integración debe preservar suficientemente el significado material, no necesariamente la representación original.

# 10. Sincronización
Otra distinción:
REAL-TIME ≠ BETTER
Necesitamos:
### SYNCHRONIZATION NEED
frecuencia/horizonte dentro del cual origen y destino deben mantener correspondencia suficiente.
Puede ser:
- inmediato;
- minutos;
- diario;
- semanal;
- bajo demanda.
### P-DT03-03
La sincronización adecuada es la requerida por el flujo; tiempo real no constituye un objetivo universal.

# 12. Information Needs
Resultan 17 NI, correspondientes a las VA.
Pero la unidad mínima de razonamiento debe preservar:
SOURCE + INFORMATION + DESTINATION + USE
Sin esos cuatro elementos no deberíamos diagnosticar fuertemente integración.
### NI-DT03-CORE
¿Qué información debe pasar, desde dónde, hacia dónde y para qué?
Solo después preguntamos:
cómo.

# 13. Grounding
Para DT-03 necesitamos fundamentación proporcional sin convertir Pymapa en un framework de arquitectura empresarial.
La familia ISO 8000 resulta nuevamente relevante porque separa calidad e intercambio de datos y contempla sintaxis, semántica y requisitos para intercambio de master data. La utilizamos como referencia conceptual, no como prescripción de arquitectura.
DAMA distingue explícitamente Data Integration & Interoperability de Data Quality, Data Security, Metadata y otras áreas de gestión, lo que respalda nuestra separación DT-02/DT-03.
En el plano técnico, estándares y prácticas de interoperabilidad muestran consistentemente que integración requiere algo más que conectividad: deben conservarse estructuras y significado suficientes para que sistemas o actores receptores puedan utilizar la información.
Para Pymapa traducimos ese conocimiento a:
business-relevant information handoffs, no a una evaluación de middleware.

# 15. Captura progresiva
## P1 · Núcleo
Preguntas SME-friendly:
“¿Dónde tienen que volver a digitar información que ya existe?”
“¿Qué información suele perderse cuando el trabajo pasa de una persona o sistema a otro?”
“¿Dónde necesitan copiar, exportar o enviar archivos para continuar un proceso?”
“¿Qué información llega tarde al siguiente paso?”
“¿Qué pasa si esa transferencia falla?”
Estas preguntas descubren handoffs materiales.

# P2 · Triggers
Profundizamos ante:
- re-digitación;
- copiar/pegar;
- conciliación recurrente;
- archivos enviados manualmente;
- múltiples versiones;
- información perdida;
- retrasos;
- errores entre sistemas;
- sincronización tardía;
- doble registro;
- export/import;
- workarounds;
- integraciones que fallan;
- dependencia de una persona;
- crecimiento de volumen;
- excepciones invisibles.
Pero:
copiar/pegar no es automáticamente una brecha.
Es un trigger.

# P3 · Discriminación causal
Ante:
“CRM y ERP no cuadran”
debemos distinguir:
SOURCE DATA QUALITY → DT-02
MAPPING ERROR → DT-03
SYNC DELAY → DT-03
TRANSFORMATION ERROR → DT-03
PROCESS TIMING → OP
MANUAL EXECUTION ERROR → posiblemente OP/PC
SYSTEM FUNCTION → DT-01
REPORT TRANSFORMATION → DT-04

# P4 · Contradicciones
### CONTR-DT03-01
SYSTEMS_CONNECTED_vs_MANUAL_RECONCILIATION
“Todo está integrado”
pero existe conciliación manual material recurrente.
No demuestra automáticamente falla, pero exige profundización.
### CONTR-DT03-02
AUTOMATED_TRANSFER_vs_MISSING_EXCEPTIONS
“Es automático”
pero nadie sabe cuándo falla.
### CONTR-DT03-03
REAL_TIME_vs_NOT_NEEDED
Existe integración compleja en tiempo real para un uso semanal.
Puede indicar:
over-integration.

# P5 · Validación
No:
“¿Sus sistemas están integrados?”
Mejor:
“Cuando ventas confirma un pedido, ¿la información que operaciones necesita llega completa y correctamente antes de preparar el pedido, sin volver a digitarla?”
Ahora podemos observar el handoff real.

# 17. Suficiencia
### SUFF-DT03-01
DT-03 alcanza suficiencia cuando los handoffs materiales permiten que la información requerida atraviese las fronteras aplicables con correspondencia, oportunidad, integridad y confiabilidad suficientes para los flujos a los que sirven.
No significa:
todos los sistemas conectados.

# Coverage
La cobertura sigue:
material flow → critical handoff → applicable requirements.
No:
aplicación → todas sus interfaces.
Esto mantiene viable el diagnóstico.

# 18. Confianza
Reutilizamos C0–C3.
Para un handoff crítico:
C1 declaración
C2 evidencia de transferencia
C3 funcionamiento repetido + excepciones suficientemente observables
La existencia de una API solo aporta:
evidencia de mecanismo.
No necesariamente:
evidencia de integración efectiva.

# Guardrails
- No preguntar primero por APIs.
- No asumir que manual = inmaduro.
- No asumir que automático = adecuado.
- No exigir tiempo real.
- No exigir integración total.
- No premiar número de integraciones.
- No penalizar export/import sin materialidad.
- No confundir integración con calidad del dato.
- No confundir integración con proceso end-to-end.
- No confundir integración con analítica.
- No confundir conectividad con integración.
- No exigir middleware.
- No exigir ESB/iPaaS.
- No exigir confirmación donde no agrega valor.
- No automatizar excepciones raras sin justificación.
- No atribuir inconsistencia automáticamente a integración.
- No asumir que duplicación implica error.
- No exigir sincronización idéntica para todos los datos.
- No ignorar handoffs persona-persona.
- No ignorar integraciones externas.
- No mantener integraciones innecesarias solo porque ya existen.

# Un concepto nuevo: Integration Debt
Debemos manejarlo cuidadosamente.
No será:
“cantidad de integraciones viejas”.
Lo definimos como candidato:
### INTEGRATION FRICTION
esfuerzo, fragilidad o complejidad recurrente generada por handoffs que ya no son suficientemente adecuados para el flujo que deben soportar.
Preferimos Integration Friction a “technical debt” porque es más observable y menos interpretativo.

# Candidatos para el Motor
### CAND-MOTOR-DT03-01
La unidad diagnóstica de integración debe ser el Information Handoff material, no la interfaz tecnológica.
### CAND-MOTOR-DT03-02
Connected, transferred, mapped, synchronized, received, usable y confirmed deben permanecer como estados distintos.
### CAND-MOTOR-DT03-03
Los requisitos de integración deben activarse condicionalmente por handoff; tiempo real, confirmación o automatización no son universales.
### CAND-MOTOR-DT03-04
Un mecanismo manual puede ser suficiente y debe juzgarse por materialidad, volumen, esfuerzo, error y sostenibilidad.
### CAND-MOTOR-DT03-05
Una inconsistencia entre origen y destino debe discriminar calidad fuente, mapping, transformación, sincronización y proceso antes de atribuir causalidad.
### CAND-MOTOR-DT03-06
La integración puede presentar UNDER-INTEGRATION u OVER-INTEGRATION.
### CAND-MOTOR-DT03-07
La suficiencia de integración debe asociarse a FLOW + HANDOFF + USE y no simplemente a una pareja de aplicaciones.
### CAND-MOTOR-DT03-08
El crecimiento de volumen/frecuencia puede invalidar un handoff previamente suficiente sin que la evaluación histórica haya sido incorrecta.

# 10. Findings y decisiones
Las 17 reglas primarias se consolidan en 8 familias de hallazgo.
| ID | Familia | Núcleo diagnóstico |
| HF-DT03-01 | Handoff material insuficientemente definido | No está suficientemente claro qué información debe pasar, entre qué contextos o para qué |
| HF-DT03-02 | Cobertura de transferencia insuficiente | Información requerida no llega completa o al destino correcto |
| HF-DT03-03 | Correspondencia semántica insuficiente | Mapping o transformación altera materialmente el significado requerido |
| HF-DT03-04 | Temporalidad/sincronización insuficiente | Información llega tarde, con frecuencia inadecuada o fuera de secuencia |
| HF-DT03-05 | Integridad de transferencia insuficiente | Información se pierde, altera o duplica materialmente durante el handoff |
| HF-DT03-06 | Handoff operacionalmente frágil | Transferencia falla o sus fallos permanecen insuficientemente visibles/tratables |
| HF-DT03-07 | Esfuerzo de integración desproporcionado | El mecanismo funciona, pero exige retrabajo o carga material injustificada |
| HF-DT03-08 | Mecanismo de integración no sostenible | Volumen, frecuencia o complejidad previsible superarán razonablemente el mecanismo actual |

## El finding debe preservar el flujo
Evitemos:
“CRM y ERP no están integrados.”
Ese finding habla de aplicaciones, no del problema empresarial.
Preferimos:
“La información de condiciones comerciales confirmadas en CRM no llega suficientemente completa y oportuna a facturación, generando validación manual recurrente antes de emitir la factura.”
Ahora tenemos:
FLOW + HANDOFF + CONDITION + CONSEQUENCE
### FIND-DT03-01
Todo finding de integración debe conservar el flujo o uso material cuya continuidad informacional está afectada.

# El mecanismo manual no es el finding
Supongamos:
pedidos se transfieren mediante CSV.
Eso es una observación.
No una brecha.
Solo se convierte en finding si produce, por ejemplo:
- retraso material;
- errores;
- carga desproporcionada;
- falta de control;
- fragilidad;
- incapacidad frente al volumen.
### CAUS-DT03-01
La existencia de un mecanismo manual no constituye evidencia suficiente de una brecha de integración.

### TRANSFORM
Modificar transformación necesaria.
### RESCHEDULE
Ajustar timing, frecuencia o secuencia.
### STABILIZE
Mejorar confiabilidad del handoff.
### CONTROL
Hacer visibles/tratables fallos y excepciones.
### SIMPLIFY
Reducir pasos, transformaciones o intermediarios.
### AUTOMATE
Automatizar cuando esté materialmente justificado.
### CONSOLIDATE
Reducir handoffs mediante consolidación de herramientas/fuentes.
### RETIRE
Eliminar integración innecesaria.
### NO_ACTION
Mantener mecanismo actual.
Esto es deliberadamente más amplio que:
CONNECT / AUTOMATE.

# ¿Cuándo automatizar?
Introducimos:
### INT-DT03-01 · MINIMUM SUFFICIENT HANDOFF
Debe preferirse el mecanismo de transferencia de menor complejidad total que satisfaga suficientemente volumen, frecuencia, oportunidad, integridad, confiabilidad y sostenibilidad requeridos por el flujo material.
La automatización gana pertinencia cuando aumenta suficientemente:
frecuencia × volumen × repetitividad × consecuencia del error × costo manual.
Pero tampoco convertimos esto en fórmula universal.

# ¿Cuándo NO integrar?
Puede ser correcto no crear una integración cuando:
- el uso no es material;
- frecuencia es baja;
- transferencia manual es suficiente;
- costo supera valor;
- información no debería compartirse;
- sistema será retirado pronto;
- flujo debería eliminarse;
- necesidad todavía es incierta.
### P-DT03-18
Una necesidad aparente de integración puede desaparecer al simplificar el proceso o eliminar una transferencia innecesaria.
Por eso OP-04 sigue siendo relevante.

# Over-integration
También puede existir:
OVER-INTEGRATION
Ejemplo:
Una pyme mantiene siete automatizaciones entre tres herramientas porque históricamente fue agregando soluciones.
Ahora:
- nadie comprende todas las dependencias;
- pequeños cambios rompen flujos;
- mantenerlas consume horas;
- dos herramientas podrían consolidarse.
No necesitamos “mejorar” las siete integraciones.
Podemos:
retirar cinco.

## La arquitectura DT construida hasta ahora
Ya tenemos tres unidades de razonamiento claramente diferentes:
DT-01 · USE → TECHNOLOGY ENABLEMENT
¿La tecnología habilita suficientemente?
DT-02 · USE → DATA NEED → CDE
¿El dato es suficientemente apto?
DT-03 · FLOW → INFORMATION HANDOFF
¿La información cruza suficientemente las fronteras?
Esto prepara muy bien DT-04 · Convertir datos en información útil para decisiones, pero allí tendremos que hacer otra separación crucial:
DATA ≠ METRIC ≠ INFORMATION ≠ INSIGHT ≠ DECISION ≠ RESULT.
DT-04 no deberá medir cuántos dashboards tiene la pyme ni si utiliza BI. Tendrá que evaluar si una necesidad real de decisión puede transformarse en información suficientemente pertinente, comprensible, oportuna y accionable, sin confundir disponer de información con tomar una buena decisión ni con lograr el resultado esperado.
Ese será el punto de partida para dimensionar orgánicamente DT-04.
